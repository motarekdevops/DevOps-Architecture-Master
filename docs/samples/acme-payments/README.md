# Sample: Acme Payments

> **Status: illustrative reference output, hand-authored.**
> These documents were written by hand to demonstrate the document contract the
> skill produces (11 files, ID scheme, ADR discipline, status taxonomy). They were
> **not** generated by a run of the skill. To judge real output quality, run the
> skill yourself against `SOURCE-INTERVIEW.md`.

This sample shows what a complete `<project-slug>-architecture.zip` looks like
when unpacked. The 11 documents in `output/` correspond 1:1 to the ZIP contract
in the root README.

## How to read it

1. Start with `SOURCE-INTERVIEW.md` — the discovery input.
2. Then `output/SRS.md` — requirements (REQ/NFR IDs originate here).
3. Then `output/System-Architecture.md` — architecture + ADR cross-refs.
4. Then `output/Full-Architecture-Decision-Records.md` — the "why".
5. `output/TEST_PLAN.md` and `output/Backlog.md` — traceability landing points.
6. `output/Design-System.md` — note the mandatory SCAFFOLD header.

## What this sample demonstrates

- **ID traceability:** every `REQ-`/`NFR-` in SRS appears in ≥1 `STORY-` in Backlog
  and ≥1 `TC-` in TEST_PLAN. Every `ADR-` cited in System-Architecture exists.
- **Status taxonomy:** controls are marked designed / proposed / implemented /
  verified — never "certified".
- **Design-System scoping:** the file opens with the SCAFFOLD header required by
  Phase 4 of the skill.
- **TBD discipline:** unknowns from the interview (SOC 2 scope, RTO/RPO,
  card-network certifications) are carried through as TBD, not invented.

## Fictional context

"Acme Payments" is a fictional B2B subscription-billing product. Any resemblance
to real systems is coincidental. No real credentials, keys, or customer data
appear in any file.
